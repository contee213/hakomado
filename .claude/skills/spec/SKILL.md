# /spec: 思いつきを仕様と Story にする

引数 (`/spec` のあとの文) が、仕様にしたい思いつき。無ければ、何を作りたいかを先に聞く。

Jira・Confluence はサイト `contee213-dev.atlassian.net` を Atlassian MCP で読み書きする (CLAUDE.md の「Jira と Confluence」)。

## 手順

1. **決まっていることを読む**
   - `docs/decisions.md` と `docs/design-guide.md` (特に 10 章のユーザーストーリー) を読む。
   - 思いつきに関わる画面・データの文書 (`docs/screen-flow.md`・`docs/screen-items/`・`docs/data-io.md`) も読む。
   - ここで決まっていることは、聞き直さない。決まりと食い違う案になりそうなら、その決まりを示してから聞く。
2. **インタビューする**
   - 決まっていないことを、1 回に 1 つから数個ずつ、選択肢つきで聞く。選択肢には、使う人から見た違いを書き、おすすめを 1 つ示す (作る手間は判断に入れない。decisions.md の決まり)。
   - どのユーザーストーリー (design-guide.md 10 章) のためか、その「うまくいっている状態」にどう近づくかを固める。
   - 画面・ボタン・言葉・保存するもの・失敗したときの動きまで固まったら、インタビューを終える。
3. **仕様のページを作る**
   - Confluence のスペース HAKO で「仕様」ページを探す。無ければスペースの直下に作る。
   - 「仕様」の下に、この機能のページを作る。書くこと: 目的 (どのストーリーのためか)、決めたこと、画面と操作、保存するもの、失敗したとき、決めなかったこと・あとに回したこと。
   - インタビューで新しく決めたことのうち、ほかの機能にも効くものは、`docs/decisions.md` や `docs/design-guide.md` に足す案として最後に伝える (ガイドに足すのはユーザーに確かめてから。CLAUDE.md の決まり)。
4. **Story に分ける**
   - 1 Story = 1 PR で終わる大きさに分ける。それぞれに受け入れ条件を書く。受け入れ条件は、使う人から見て確かめられる形にする。
   - 作る前に、Story の一覧 (タイトル・受け入れ条件・順番) を見せて、ユーザーの OK を待つ。直してと言われたら直して、もう一度見せる。
5. **Story を作る**
   - OK をもらったら、Jira の HAKO に Story を作る。説明に受け入れ条件を書き、仕様のページをリンクする。
   - 作った Story のキーと、仕様のページの URL を伝える。始めるときは `/start <キー>` と添える。

## 止めるとき

- Atlassian MCP につながらない、スペース HAKO・プロジェクト HAKO が見つからない、権限が無い: 無理に進めず、何が起きたかを伝える。
